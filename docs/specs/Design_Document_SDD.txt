2. Architecture Overview
RVAH is designed as a modular Rust workspace. The core application owns domain models, state transitions, permission decisions, and playback orchestration. Add-ons run in a sandboxed component runtime and communicate with the host through a narrow typed interface. The player is abstracted behind a trait so the project can start with a pragmatic backend and change implementation without changing the add-on SDK.

2.1 Design principles
Host-owned security: add-ons never receive direct OS, network, or credential access unless the host mediates it.
Small typed SDK: add-ons return normalized catalogs, media items, and playable sources rather than manipulating UI widgets directly.
Playback separation: add-ons discover and resolve; the host validates and plays.
Replaceable adapters: UI toolkit, player backend, keychain, and repository transport are adapter boundaries.
Contract-first add-on API: SDK changes are versioned and verified with compatibility tests.
No Kodi dependency: names, code, package format, and APIs are independent.
3. Technology Decisions
Decision area
Recommended design
Rationale
Language/build
Rust workspace with multiple crates managed under one Cargo.lock.
Keeps core, adapters, SDK, and tools versioned together while retaining modular boundaries.
Add-on runtime
Sandboxed WebAssembly components via Wasmtime-compatible host interface.
Provides isolation, quotas, typed imports/exports, and a path to multi-language add-ons without loading arbitrary native code.
Player backend
Abstract PlayerBackend trait; MVP backend may use mpv/libmpv or process IPC. GStreamer remains an adapter option.
Video playback is complex; using a mature backend reduces codec, subtitle, and streaming risk.
Storage
SQLite for relational app state; OS keychain or encrypted vault for secrets; cache directory for artwork and transient data.
Simple, portable, debuggable, and easy to migrate.
Networking
Host-owned async HTTP client with per-add-on egress allowlists and redaction-aware logging.
Prevents unrestricted sockets and supports user-visible permissions.
UI
UI toolkit behind adapter; MVP can use a fast desktop toolkit and later add a TV/remote-first shell.
Avoids locking the domain model to a single presentation framework.

Player note: Directly writing a full video player is not recommended for MVP. The design assumes a mature backend and focuses project effort on add-on hosting, permissioning, UX, metadata, and source resolution.

5. Add-on Package and Manifest Design
An RVAH add-on is a signed package containing a manifest, one or more runtime modules, assets, translations, and optional documentation. The manifest is the security boundary: it declares what the add-on can do, what domains it can contact, what settings it exposes, and which host SDK range it supports.

6. Add-on SDK Interface
The host exposes a narrow API. Add-ons provide catalog/search/resolve functions and call host imports for HTTP, storage, auth, logging, and settings. All host imports are capability-checked at runtime.

7. Core Flows
7.1 Browse flow
User opens an enabled add-on from the UI.
UI sends OpenProvider command to rvah-core.
Core checks add-on status and permission grants, then calls rvah-addon-host list(None, None).
Add-on host invokes sandboxed module with quotas and a cancellation token.
Add-on returns Page containing normalized items.
Core stores transient navigation state and emits a view model to the UI.
UI renders items; selecting a directory repeats the call with a path or cursor.
7.2 Resolve and playback flow
User selects MediaItem  -> Core validates item and add-on state  -> Add-onHost.resolve(item_id, source_id)  -> Add-on returns PlayableSource(s)  -> Core validates URL/protocol/header policy  -> PlayerController.load(source, resume_position)  -> Player emits buffering/progress/error/completed events  -> Core persists resume/watched state
7.3 Auth flow
Add-on declares an auth capability and requests a host-managed auth action when account access is required.
Host presents provider name, requested scopes/secrets, and user action steps.
Host stores tokens/secrets outside the add-on sandbox; add-on receives opaque account status or host-provided secret only when permitted.
Refresh, expiration, and revocation are handled centrally so the user can manage accounts in one place.
8. Player Subsystem Design
Component
Design
PlayerController
State machine owned by core: Idle, Loading, Buffering, Playing, Paused, Seeking, Ended, Error.
PlayerBackend trait
load, play, pause, stop, seek, set_volume, set_track, set_subtitles, observe_events.
mpv adapter
MVP candidate using mpv/libmpv or IPC. Handles broad codecs, subtitles, streaming protocols, and hardware acceleration through backend configuration.
GStreamer adapter
Alternative for tighter pipeline control, platform integration, or future DRM-provider workflows.
Source validator
Rejects unsupported protocols, expired URLs, unsafe local paths, unapproved headers, or malformed subtitle descriptors.
Progress persister
Debounced progress updates to data store; marks watched according to configurable completion threshold.

9. Security and Permission Design
Risk
Mitigation
Malicious add-on exfiltrates secrets
Secrets are stored in host vault; access requires manifest declaration, user grant, and redaction-aware host APIs.
Add-on performs broad web scraping or contacts arbitrary hosts
HTTP calls go through host client with DNS/domain allowlists, request quotas, and logging.
Add-on hangs or allocates excessive memory
Runtime memory limits, fuel/epoch interruption, wall-clock timeouts, cancellation tokens, and kill/quarantine policy.
Package tampering
Repository signing, package hashes, local signature verification, and immutable version records.
Insecure update
Update only from trusted repository metadata; permission expansion requires explicit re-approval.
Log leakage
Central logger redacts tokens, cookies, authorization headers, API keys, and configured secret names.
License contamination
No copied Kodi code/assets. Third-party dependencies tracked in SBOM and reviewed for license compatibility.

11. Error Model
Class
Examples
User treatment
User-actionable
Auth expired, permission missing, account quota exceeded.
Show clear action button: sign in, grant permission, retry later.
Recoverable
Provider timeout, temporary network failure, unavailable source.
Offer retry and alternative source; retain navigation state.
Developer/actionable
Malformed add-on response, SDK mismatch, schema violation.
Log diagnostics, show generic message, optionally disable add-on after repeated failures.
Fatal host
Database corruption, player backend missing, keychain unavailable.
Show safe error screen and diagnostic export; avoid data loss.

12. Excluded Kodi/Media-Center Features
Feature
Decision
Kodi Python APIs
Not implemented. A future migration tool could port simple provider logic to the RVAH SDK.
Skins/theme engine
Not implemented. Provide one host UI with limited theming.
Music/photos/games/weather
Not implemented for product focus and testability.
PVR/DVR/EPG
Not implemented; considered a separate product line.
Full local library scraping
Deferred. Metadata is provider-supplied or cached from add-on results.
Network file servers
Deferred unless required by a future local-file provider.
Raw torrent engine
Deferred due to legal, network, storage, and UX complexity.
