2. Product Summary
RVAH is a video-first application and add-on host written in Rust. It allows users to install provider add-ons that expose browsable catalogs, search results, playable source candidates, and resolver flows. The host owns the user interface, add-on sandbox, credential storage, network permissioning, and playback engine.
The product is intentionally narrower than Kodi. It borrows the successful user interaction pattern of “browse directory-like lists, select an item, resolve to a playable source, and hand that source to a player,” but it does not implement Kodi compatibility, Kodi skins, Kodi Python APIs, PVR, music, photos, games, or a full local media-center library.
In scope
Out of scope for MVP
Video add-on browsing, search, resolving, and playback.
Kodi Python add-on compatibility or emulation.
Custom add-on SDK with stable host APIs.
Music, photo, game, weather, PVR/DVR, and live-TV guide subsystems.
Sandboxed add-on runtime with permissions.
Full theme/skin engine or arbitrary script UI windows.
Debrid/service-style authenticated resolver workflows.
Bundled content piracy sources, DRM circumvention, or illegal scraping features.
Local app state: installed add-ons, settings, credentials, favorites, resume/watched state.
Large local media library scraping and network file servers.

2.1 Goals
Deliver a minimal but extensible video add-on host that can install, run, permission, and update add-ons safely.
Use Rust for the core application, runtime, data layer, network layer, and player orchestration.
Make add-on development simpler than Kodi add-on development by defining a small, typed SDK rather than exposing a full media-center API.
Keep the host neutral: add-ons describe catalogs and resolve media sources, while the host controls playback, credentials, UI, and security boundaries.
Enable legal service integrations and user-provided account/API workflows without bundling unauthorized content sources.
2.2 Success criteria
Criterion
Target
MVP browsing
A fixture add-on can return nested directories, media items, pagination, artwork, and metadata.
MVP playback
A fixture add-on can resolve at least direct MP4 and HLS URLs; the player can start, pause, seek, stop, and report progress.
MVP security
An add-on cannot access network, storage, credentials, or OS resources unless explicitly granted by manifest permissions and user approval.
MVP distribution
The host can install a signed add-on package, verify metadata, enable/disable it, and uninstall it cleanly.
MVP maintainability
Core crates have automated tests, contract tests for the SDK, and mock player/runtime tests in CI.

3. Assumptions and Constraints
ID
Assumption or constraint
A-01
The first target is desktop-class devices: Windows, macOS, and Linux. TV/mobile ports are future work.
A-02
The add-on SDK is new and does not promise Kodi API compatibility.
A-03
The application will not include Kodi source code or assets unless the project explicitly accepts the related license obligations.
A-04
Raw torrent streaming is deferred. Debrid or account-backed resolver APIs may be supported as add-ons when legally configured by users.
A-05
The host must not bypass DRM, paywalls, geographic restrictions, or terms of service. Any DRM support must use lawful platform/provider mechanisms.
A-06
The host must be resilient to malicious, buggy, slow, or abandoned add-ons.

4. User Roles and Primary Use Cases
Role
Needs
Viewer
Install trusted add-ons, authenticate services, browse/search videos, play streams, manage favorites, and resume playback.
Add-on developer
Use a typed SDK, test locally, declare permissions, package/sign releases, and debug host interactions.
Repository maintainer
Publish add-on metadata, review permissions, rotate signatures, and deprecate unsafe versions.
Operator/reviewer
Inspect logs, reproduce bugs, verify security boundaries, and approve release gates.

4.1 MVP use cases
Use case
Summary
UC-01 Install add-on
User selects an add-on package or repository entry. Host verifies signature, shows permissions, installs, and enables it.
UC-02 Browse catalog
User opens an add-on and navigates directory-like pages supplied by the add-on.
UC-03 Search
User searches one add-on or all installed add-ons; host presents normalized media results.
UC-04 Authenticate service
User completes device-code/OAuth/API-key flow; host stores tokens in the secret vault.
UC-05 Resolve source
User selects a media item; add-on returns one or more playable sources or a resolver action.
UC-06 Play video
Host hands a playable source to the player, applying allowed headers, subtitles, and resume state.
UC-07 Recover from failure
Host surfaces clear errors for add-on failures, network errors, auth expiration, and unsupported media.

6. Non-Functional Requirements
Category
Requirement
Performance
Cold start target under 3 seconds on a modern desktop; cached page render under 500 ms; uncached provider page target under 2 seconds excluding external service latency.
Playback responsiveness
From resolved playable URL to first frame target under 5 seconds for normal broadband/HLS conditions.
Reliability
Add-on crash, timeout, or malformed response must not crash the host; host should recover by disabling or quarantining repeated offenders.
Security
All untrusted add-ons run under least privilege, with explicit permissions, domain allowlists, quotas, and isolated state.
Privacy
Secrets and personally identifiable data are stored locally where possible, redacted from logs, and removable by the user.
Portability
Core crates shall avoid OS-specific assumptions; platform adapters shall isolate windowing, keychain, and media-output differences.
Maintainability
Core APIs shall be versioned, documented, and covered by unit, integration, and contract tests.
Accessibility
UI shall support keyboard navigation, visible focus states, readable scaling, and basic screen-reader labels where the UI toolkit supports them.
Legal/compliance
The app shall not bundle unauthorized sources or mechanisms for bypassing access controls; add-on repository policy shall prohibit illegal content facilitation.
